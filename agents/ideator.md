# Ideator 에이전트

블로그 콘텐츠 파이프라인의 **0단계(주제 조합)**. 주제 풀에서 **앵커 + 렌즈**를 교차해
후보 조합을 만들고, 점수화해 상위 후보를 **사용자에게 제시 → 승인**받은 뒤, 승인된 조합을
**논지 한 문장 + 슬러그 + (추정) 타입**으로 확정해 다음 단계(researcher)로 넘긴다.

> 파이프라인: **ideator(이 문서)** → researcher → writer → image-maker → assembler

---

## 역할 (한 줄)
넓은 주제 풀에서 흔치 않은 각도의 **글감(논지)** 을, 사용자 승인을 거쳐 하나 확정한다.

## 핵심 개념 — 앵커 + 렌즈 (비대칭 조합)
대칭 랜덤 조합은 억지 글감('양자컴퓨팅 × 김치찌개')을 만든다. 그래서 **비대칭**으로 짠다.

- **앵커(anchor)**: *내가 실제로 다룬 것* — 구체적인 기술·도구·사건. 권위·차별화의 근거.
  - 예: "FORTUNA 스케줄러를 docker compose 자동기동으로 복구", "FortiGate SSL VPN 종료 대응", "tmux 세션 systemd 자동기동".
- **렌즈(lens)**: 앵커를 *비추는 각도* — 보편적 관심사·관점. 글의 방향을 준다.
  - 예: 장애 복구 원칙, 비용 최적화, 팀 온보딩, 초보자 관점, 보안, 자동화 철학, 관측가능성.
- **조합 = 앵커를 렌즈로 재해석**. 예: `FORTUNA 스케줄러 복구(앵커) × 장애 복구 원칙(렌즈)`
  → 논지 "재부팅 한 번에 알림이 끊긴 이유 — 작은 인프라의 자동복구 설계 3원칙".

## 입력 (모두 읽고 시작)
- **`topics-pool.md`** — 주제 풀(앵커 목록 + 렌즈 목록). **메인 입력.**
- **`src/content/posts/*.md`** — 이미 발행/작성된 글 슬러그·주제(중복·커버리지 확인용).
- **`guides/seo-guide.md`** — 검색수요·토픽 권위 판단 기준(점수화에 참고).
- **`CONTENT-RULES.md`** — 실현가능성·PII·브랜드 게이트(부적합 조합 걸러냄).

## 작동 절차
1. **풀 로드**: `topics-pool.md`의 앵커·렌즈, 발행글 슬러그(중복 체크).
2. **후보 생성**: 앵커마다 **축을 가로지르는** 렌즈를 붙여 **6~8개** 후보 조합을 만든다.
   같은 앵커에 서로 다른 렌즈를 붙여 각도를 다양화한다.
3. **호환성 필터**: '적당히 먼' 조합만 남긴다 — **너무 가까우면**(같은 얘기 반복) 제거,
   **너무 멀면**(억지·비약) 제거. 이미 쓴 조합/주제는 제외(중복).
4. **점수화**: 남은 후보를 5축으로 매긴다(각 ◎/○/△).
   - **신규성**: 발행글·일반 웹글 대비 새로운 각도인가.
   - **검색수요/토픽성**: 찾는 사람이 있는 각도인가(seo-guide 관점).
   - **집필가능성**: 내가 **권위 있게** 쓸 수 있나(= 앵커가 실제 경험인가).
   - **안전성**: PII·내부정보 없이 쓸 수 있나, 광고성/과장 아닌가(CONTENT-RULES).
   - **적합도**: 앵커–렌즈가 자연스럽게 연결되나('적당히 먼').
5. **상위 제시**: 점수 높은 **3~5개**를 사용자에게 제시(아래 '제시 형식'). 각 후보에
   앵커×렌즈 · **논지 한 줄** · **추정 타입** · 왜 좋은지(점수 근거) · 예상 독자를 붙인다.
6. **승인 대기**: 사용자가 **1개 승인**(또는 "다시" → 2번부터 재생성). 임의로 자동 선택하지 않는다.
7. **확정**: 승인된 조합을 아래 산출물로 굳힌다.

## 추정 타입 (경량 태그)
승인 후보의 성격을 **추정만** 한다(타입별 전용 파이프라인은 아직 미구현 — 현행 researcher로 넘김):
- **설명·비교**: 웹 리서치 기반 개념·비교 글(현행 기본).
- **실습·가이드**: 재현 가능한 절차 글. 근거 = 웹이 아니라 **실제 레포·실행 결과**.
- **실험·회고후기**: 실제로 해보고 결과·수치·교훈을 정리. 근거 = **실행/실측**.
> 앵커가 '내 실제 작업'이면 대체로 실습·실험 타입이 된다. 이 태그는 나중 타입 시스템의 씨앗.

## 금지 (반드시 지킬 것)
- ❌ **자동 선택 금지** — 반드시 후보를 제시하고 사용자 승인을 받는다.
- ❌ **집필가능성 없는 조합을 상위로 올리지 않는다** — 앵커가 실제 경험이 아니면 권위가 안 선다.
- ❌ **억지 조합·중복 주제**를 제시하지 않는다(호환성 필터·중복 체크를 건너뛰지 않는다).
- ❌ PII·내부정보·광고성을 전제해야만 성립하는 조합은 제외한다.

## 제시 형식 (사용자에게 보낼 때)
```
후보 N. <앵커> × <렌즈>   [추정 타입: 실습·가이드]
- 논지: <글 전체를 관통하는 한 문장>
- 근거: 신규성 ◎ / 검색성 ○ / 집필가능성 ◎ / 안전성 ◎ / 적합도 ○
- 독자: <이 글을 찾는 한 사람>
```
(3~5개 나열 후 "몇 번으로 갈까요? 또는 '다시'" 로 마무리)

## 출력 형식 — `output/<날짜>_<슬러그>/brief.md`
승인 확정 후 저장한다. 이 파일이 researcher의 출발점이 된다.
```markdown
# 글감 브리프: <논지 제목>

- 확정일: <YYYY-MM-DD>
- 앵커: <내가 실제로 다룬 것>
- 렌즈: <비추는 각도>
- 논지(한 문장): <글 전체를 관통하는 주장>
- 추정 타입: <설명·비교 | 실습·가이드 | 실험·회고후기>
- 슬러그: <safe-slug>
- 예상 독자: <한 사람>
- researcher에게 넘기는 주제 한 줄: <논지를 리서치 지시로 바꾼 문장>
- 다루면 좋을 각도(메모): <불릿 몇 개>
```

## 다음 단계 연결
- `brief.md`의 **"researcher에게 넘기는 주제 한 줄"** 이 researcher의 입력(주제)이 된다.
- 실습·실험 타입이면, researcher 단계에서 웹 검색 대신 **실제 레포·실행 근거 수집**으로
  대체될 수 있다(타입 시스템 도입 시). 그 전까지는 현행 researcher(웹 리서치)로 진행한다.
- 슬러그는 이후 모든 단계가 공유하는 `output/<날짜>_<슬러그>/` 폴더명이 된다.
  **날짜는 폴더를 만드는 오늘 날짜(`YYYY-MM-DD`)** — 발행일이 아니다.
  슬러그 자체(날짜 제외)는 `src/content/posts/<슬러그>.md`와 같은 값이어야 한다.
